# NGINX2Root 연구 저장소 구축 계획 — 분석 · e2e 익스플로잇 · 방어자 가이드

## Context

2026-11-18 공개된 NGINX2Root(NGINX CVE 5건 + Linux SCTP LPE 체인)를 대상으로, OpenJDK2Shell 저장소의 연구 방법론(F/P/H 분리, 4-arm 실험, episode 기록, canary 정책)을 그대로 계승해 **① 취약점 분석 → ② e2e 익스플로잇 개발(5건 전체 시도) → ③ 방어자 가이드**를 수행하는 새 저장소를 `/Users/1004276/Downloads/nginx`(현재 빈 디렉토리)에 구축한다.

**사용자 결정사항**: Mac(arm64) + DFIRtx 랩(EPYC Genoa, AVX-512) 병행 / CVE 5건 모두 시도 / 공개 PoC 재현·검증 + 독자 개선 시도.

**핵심 제약(정직하게 기록)**:
- Mac은 arm64 → Docker amd64 에뮬레이션으로 AVX-512 불가. **풀 RCE(ASLR 우회~코드실행)는 DFIRtx에서만 가능**. Mac에서는 크래시 트리거·프레임 로직·정적 분석 담당.
- 123633/123634/121810/113425는 공개 PoC 없음 → 트리거(크래시) 개발까지가 1차 목표, RCE 확장은 게이트로 판정.
- **정책(OpenJDK2Shell 계승)**: 자체 랩 대상만, 페이로드는 무해 canary(id, touch)만, 프리미티브 확정 전 무기화 없음.

## 실행 단계

### Phase 0 — 기준선·자료 확보 (Mac)
1. 폴더 구조 + git init + `.gitignore` + README/HANDOFF/GOAL 뼈대
2. `poc-external/`에 Rapid7 PoC 클론(별도 격리 디렉토리, 참조만), `nginx-src/`에 release-1.31.8/1.31.9 소스 확보
3. `vuln-analysis-2026-11-19.md`: 5건 F/P/H 기준선 (첨부 비교문서 [R1]-[R12]를 근거 목록으로 고정)

### Phase 1 — 루트코즈 분석 (정적, Mac)
1. **123007**: 1.31.8↔1.31.9 diff로 수정 커밋 특정 → `ngx_http_v2` 흐름제어 언더플로 지점·OOB 도달 경로 소스 레벨 문서화
2. 나머지 4건: UAF 지점·트리거 조건(필요 config: proxy/draining, resolver+mirror, http3, mail) 문서화 — 공개 정보 없는 부분은 [미확인] 표기
3. `EXTERNAL-REVIEW`: Rapid7 `exploit.py` 단계별 리뷰(16 보조 연결·히프 프로파일·leak·ASLR·콜백 조작) — 외부 주장 vs 코드 사실 분리

### Phase 2 — 랩 구축 (Mac + DFIRtx)
1. `ops/docker` 4-arm: **A1 취약(1.31.8+h2 on) / A2 패치(1.31.9) / A3 완화(1.31.8+h2 off) / A4 대조(정상 부하)** + 4건 노출용 conf 변형(proxy 백엔드·동적 resolver+mirror·QUIC·mail auth_http 시뮬레이터)
2. **E0 캘리브레이션 실험(우선)**: Mac 에뮬레이션에서 123007 크래시 트리거 가부 확인 → 로컬/원격 역할 분담 확정
3. 계층: `h2_hunt` 로그포맷, error.log/`coredumpctl`, `ss`, auditd execve 규칙 — 탐지 룰 실측 근거 확보
4. DFIRtx: 기존 랩 컨텍스트 재활용(접근 방법은 실행 시점에 확인), linux-amd64 네이티브 타겟 배포

### Phase 3 — 트리거 개발 (CVE별, 판정어: 확정/지지됨/미지지/관측불가)
- `trigger_123007`: 공개 트리거 포팅·검증 → 크래시 확정 (DFIRtx + 가능하면 Mac)
- `trigger_123633`: h2 연결 draining + 백엔드 경합 자체 구성
- `trigger_123634`: 동적 resolver + mirror 서브리퀘스트 + DNS 지연 경합
- `trigger_121810`: HTTP/3(QUIC) 스트림 종료 경합 (aioquic 클라이언트)
- `trigger_113425`: mail 인증 프록시 흐름 클라이언트 + auth_http 시뮬레이터
- 각 결과는 episode/attempt JSON + `ESCALATION-STATUS` 문서화. **부정 결과도 보존**

### Phase 4 — e2e 익스플로잇 (123007 우선, DFIRtx)
1. `e2e_123007.py`: Rapid7 체인 재현(canary 명령으로 성공 판정) → 신선 컨테이너 조건에서 재현율 실측(N episode)
2. 캐릭터라이징: 부하 걸린 worker·대역폭·동시 클라이언트별 성공률 (A1↔A4 비교)
3. **독자 개선 시도**: (a) 전송량 절감(프레임/윈도 최적화), (b) glibc·히프 프로파일 변형 일반화, (c) AVX-512 비의존 경로 탐색([미확인] 명시), (d) 재시도/안정화 로직 — 개선 성공률도 동일 프로토콜로 측정
4. **게이트**: 트리거가 미지지인 CVE는 e2e 확장 없음(PIVOT: 문서·방어 가이드만). 프리미티브 확정 시에만 e2e 확장

### Phase 5 — 방어자 가이드 + ops 스크립트
1. `DEFENDER-GUIDE.md`: OpenJDK2Shell v4 구조 계승 — `0. 가장 중요한 한 가지 / 1. 자산 식별 / 2. 노출면 축소 / 3. 탐지(A: worker 자식 프로세스, B: 이상 연결, C: 로그 시그니처, D: 크래시) / 4. 완화(★root cause 직접 완화 구분) / 5. 패치 / 6. IR 플레이북 / 7. 한계(정직)`
2. 탐지 룰은 **랩 공격 트래픽 실측**으로 근거 확보(공격 episode vs A4 정상부하 대조, 오탐률 포함)
3. `inventory.sh`(버전/기능/노출 점검) · `monitor.sh`(크래시·자식프로세스) · `mitigate.sh`(http2 off 등) · `detect-rce.sh` — 4-arm 랩에서 드라이런 검증
4. 커널 SCTP LPE 체인은 문서·점검 항목으로만 다룸(실제 권한상승 실증은 범위 외)

### Phase 6 — 산출물 정리
- README 산출물 표 갱신, `ESCALATION-STATUS` 최종본, HANDOFF.md 작성, git 커밋

## 게이트 (RESEARCH-PLAN에 명문화)
- **G1** (P1→P3): 5건 루트코즈·조건 도출 완료 시 CONTINUE
- **G2** (P3→P4): 123007 DFIRtx 크래시 재현 시 e2e 착수, 미지지 시 PIVOT
- **G3** (P4 내): e2e 재현 실패해도 캐릭터라이징 부정 결과 + 방어 가이드는 완주 (부정 결과 포함 정책)

## 검증 방법
- 각 트리거/e2e는 4-arm 랩에서 A1(취약)에서만 크래시/RCE 발생, A2(패치)·A3(완화)에서 미발생 확인 → 취약점 특이성 실측
- e2e 성공 판정 = canary 파일/`id` 출력 존재 + worker 자식 프로세스 관측(모니터링 스크립트로 이중 확인)
- 방어자 가이드 탐지 룰: 공격 episode 재생 시 탐지됨 + A4 정상 부하에서 오탐 없음 검증
- 모든 실험 결과는 episode/attempt JSON으로 재현 가능한 형태로 보존
